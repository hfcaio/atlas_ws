Missão Icarus — guia de uso

Como correr, configurar e estender a missão de busca-e-órbita do ATLAS. O nó recebe a posição de um alvo, constrói um plano de voo em tempo real e executa-o de forma autónoma via MAVROS.

Visão geral

O que este código faz

O executável mission (pacote icarus_tests, ficheiro icarus_mission_sem_drop.py) sobe um nó ROS 2 chamado autopilot_node. Ele espera uma coordenada GPS de um alvo, calcula a rota, envia uma missão MAVLink ao controlador de voo (FCU) e arma o veículo para a executar.

A missão gerada: descolar a 5 m → aproximar-se do alvo com margem de segurança → orbitar o alvo em 20 waypoints (raio 7,5 m) → pousar. "Sem drop" é a variante que não larga carga — apenas reconhece em órbita.

Para o mapa visual do percurso, vê o explicador animado da missão.

Antes de começar

Pré-requisitos

  • Estás dentro do container atlas-sim:humble (todo o ROS/Gazebo/ArduPilot vive lá).
  • O workspace já foi inicializado e compilado uma vez (atlas-ws-init && atlas-deps && atlas-build).
  • A simulação está no ar: Gazebo + SITL + MAVROS, tipicamente via ap-sim copter.
# 1 — sobe Gazebo + SITL + MAVROS (painéis tmux)
xhost +local:docker && docker compose run --rm dev ap-sim copter

Espera até veres no MAVProxy pre-arm good e o EKF com origem — sinal de que o FCU aceita comandos.

Correr

Início rápido

Com a simulação a correr, num segundo terminal:

# compilar (só se mexeste no código)
docker compose run --rm dev atlas-build --packages-select mavros_library icarus_tests

# lançar a missão + um alvo falso (fake_target)
docker compose run --rm dev ros2 launch atlas_mission mission.launch.py

O launch publica um alvo falso e, após 3 s, arranca o nó de missão. Podes passar argumentos:

# mudar a posição do alvo
ros2 launch atlas_mission mission.launch.py target_lat:=-35.3605 target_lon:=149.1652

# voo real / confirmação manual do alvo no terminal
ros2 launch atlas_mission mission.launch.py auto_confirm:=false

# correr o nó sozinho, sem o alvo falso (publicas tu o alvo)
ros2 run icarus_tests mission
Argumento do launchDefaultPara quê

auto_confirmtrueAceita o alvo sem pedir confirmação (necessário em SITL sob ros2 launch).

Hardware

Correr no drone real

O código é o mesmo — o que muda é a quem o MAVROS se liga e a origem do alvo. Em vez do SITL, o MAVROS aponta para o controlador de voo físico; em vez do fake_target, publica o alvo o teu sistema de deteção real.

Segurança primeiro. Isto arma e move um veículo real. Faz o primeiro teste sem hélices, num espaço aberto e autorizado, com um piloto ao comando do rádio pronto a assumir o controlo (interruptor de modo em STABILIZE/LOITER) e a desarmar. Confirma o geofence e a altitude antes de qualquer voo autónomo.

1. Ligar o MAVROS ao FCU

Em vez do ap-sim, sobe só o MAVROS apontado ao link real (USB, telemetria série ou UDP de um companion). O fcu_url depende do teu hardware: 

# USB direto (ex. Cube/Pixhawk em /dev/ttyACM0)
docker compose run --rm dev ap-mavros serial:///dev/ttyACM0:921600

# rádio de telemetria (ex. /dev/ttyUSB0 a 57600)
docker compose run --rm dev ap-mavros serial:///dev/ttyUSB0:57600

# companion via UDP
docker compose run --rm dev ap-mavros udp://:14550@

O container precisa de acesso ao dispositivo série (ex. correr com --device /dev/ttyACM0 ou o grupo dialout). Confirma a ligação com ros2 topic echo /mavros/state — deve vir connected: true.

2. Fornecer o alvo (sem fake_target)

Não uses o mission.launch.py (ele lança o alvo falso). Corre o nó de missão sozinho e deixa o teu detetor publicar a coordenada real: 

# alvo vem do teu sistema de visão/deteção, em NavSatFix
ros2 run icarus_tests mission --ros-args -p auto_confirm:=false

# o teu detetor publica em:
#   /mavros/mission/vtol_person_position  (sensor_msgs/NavSatFix)

Com auto_confirm:=false, o nó pede confirmação S/N no terminal antes de construir a missão — uma última validação humana da posição do alvo.

3. Antes de armar

  • Pré-arm real: espera GPS 3D lock, EKF pronto e bússola calibrada. O ArduPilot rejeita o arm se algo falhar — vê a razão em /mavros/statustext/recv.
  • Altitude & frame: a missão descola a ALTITUDE_FINAL = 5 m e orbita a 7,5 m do alvo. Confirma que estas margens fazem sentido no local; se não usas base de terreno, troca TERRAIN_ALT por RELATIVE_ALT.
  • Geofence: em SITL está desativado no código. Para voo real, reativa o bloco de geofence (ou define um no FCU) para conter o veículo.
  • Fuga de emergência: tem sempre o rádio a postos e o tópico de abort à mão (secção Abort & segurança).
O que não muda: a sequência de arranque é idêntica à do SITL — GUIDED → armar → AUTO → MISSION_START. Se validaste o comportamento em SITL, o FCU real segue a mesma lógica; a diferença está nos sensores e no ambiente, não no código.
Interno

Como funciona, por ordem

  • 1. Init & conexão — init_all() cria subscribers/clients MAVROS; wait_for_connection() espera o heartbeat.
  • 2. Aguardar alvo — subscreve vtol_person_position; com auto_confirm aceita o primeiro, senão pede S/N.
  • 3. Construir a missão — a partir da posição do drone e do alvo, gera takeoff + aproximação + 20 waypoints em círculo + land.
  • 4. Upload — new_mission() limpa e envia a missão ao FCU; a confirmação é por contagem + sequência de comandos.
  • 5. Arranque — run_mission() confirma a missão no FCU e faz GUIDED → armar → AUTO → MISSION_START.
  • 6. Executar — acompanha mission_reached.wp_seq até ao fim; um abort força LAND.
Porque GUIDED antes de AUTO? O ArduCopter recusa armar já em modo AUTO (Auto mode not armable). Arma-se em GUIDED — que é armável — e só depois se passa a AUTO e se dispara a missão com MISSION_START.

Parâmetros & constantes

Contrato de I/O

Tópicos & serviços

O nó fala com o exterior por dois tópicos próprios, e com o FCU pela mavros_library.

TópicoTipoPapel
/mavros/mission/vtol_person_position subNavSatFixPosição GPS estimada do alvo.
/mavros/mission/abort_command subBooltrue → aborta e comanda LAND.

Internamente usa tópicos e serviços MAVROS padrão: state, global_position/global, mission/waypoints, mission/reached (subscrições); set_mode, cmd/arming, cmd/command, mission/push, mission/clear (serviços).

Regra de ouro do MAVROS aqui: as subscrições a tópicos de estado/sensor precisam de QoS BEST_EFFORT / VOLATILE. Com o QoS default não chega nada — é o erro mais comum. A mavros_library já usa o perfil certo; se subscreveres um tópico novo à mão, copia-o.
Reutilizar

API da mavros_library

A regra do projeto: não falar com tópicos/serviços crus no nó de missão — usar a lib, e se faltar algo, estendê-la. Blocos principais:

sequences/

Rotinas de alto nível (recebem node + prefix):

  • init_all(node, ["mavros"])
  • wait_for_connection(node, ["mavros"])
  • new_mission(node, prefix, waypoints)
  • run_mission(node, prefix) → bool
  • set_geofence(node, prefix, fences)
commands/

Chamadas a serviços, com confirmação e timeout:

  • set_mode(node, prefix, "AUTO")
  • cmd_arming(node, prefix, True)
  • cmd_mission_start(node, prefix)
  • mission_push / mission_clear / mission_set_current
commands/mission_commands/

Construtores de waypoints (devolvem um Waypoint):

  • mission_add_takeoff(z_alt=5.0)
  • mission_add_waypoint(x_lat, y_long, z_alt, yaw)
  • mission_add_land(x_lat, y_long, z_alt)
  • … loiter, RTL, fences, rally, etc.
utils/

Geo & comparações:

  • calculate_bearing(a, b)
  • calculate_horizontal_distance_global(a, b)
  • convert_local_to_global_coordinates(...)

Esqueleto mínimo de um nó que usa a lib:

from mavros_library.commands import *
from mavros_library.sequences import init_all, wait_for_connection, new_mission, run_mission

init_all(self, ["mavros"])
wait_for_connection(self, ["mavros"])

self.drone.mission.extend([
    mission_add_takeoff(z_alt=5.0),
    mission_add_waypoint(x_lat=lat, y_long=lon, z_alt=5.0, yaw=0.0),
    mission_add_land(x_lat=lat, y_long=lon, z_alt=0),
])

new_mission(self, "mavros", self.drone.mission)
if not run_mission(self, "mavros"):
    self.trigger_abort()
Segurança

Abort & paragem

  • Publica true em /mavros/mission/abort_command a qualquer momento → o nó comanda LAND imediato.
  • Ctrl-C no terminal do nó também dispara o abort (via KeyboardInterrupt).
  • Qualquer passo do arranque que falhe (modo, arm, mission start) aborta com LAND e log explícito — o nó não fica preso.
# abort manual a partir de outro terminal
ros2 topic pub -1 /mavros/mission/abort_command std_msgs/Bool "{data: true}"
Quando corre mal

Troubleshooting

SintomaCausa & solução
Não chega telemetria
(state/posição vazios)		QoS errado. Tópicos MAVROS de estado exigem BEST_EFFORT/VOLATILE. A lib já usa; num subscriber novo, copia o perfil.
Arm: Auto mode
not armable		Não se arma em AUTO. Resolvido: run_mission arma em GUIDED e só depois passa a AUTO + MISSION_START.
Push da missão
demora ~15 s		Resolvido: a confirmação passou a ser por contagem + sequência de comandos, em vez de igualdade campo-a-campo (o FCU reescreve o waypoint 0/home).
Não descola em AUTOFalta o gatilho. Em AUTO no chão o copter espera por MISSION_START (ou throttle). O run_mission já o envia.
Altitude estranha
em voo		Os waypoints usam o frame TERRAIN_ALT. Sem base de terreno, troca para RELATIVE_ALT nos mission_add_*.

Para ver a razão real de uma rejeição do FCU:

docker compose run --rm dev ros2 topic echo /mavros/statustext/recv
